# Diagnosing a run

Use this guide to work out where a demo run stopped, what restarted, and
which evidence another LeKiwi developer needs to reproduce it. The demo
provides transcripts, identity comparisons and lifecycle events. It does
not automatically diagnose a camera, USB, calibration or network fault.

Run commands from the repository root or extracted release root. Start
with [segment 1](segment-1-stub.md) if you have not run the demo yet. For
a live robot, follow [Safety](../SAFETY.md) and the
[stopping procedure](stopping-and-cleanup.md) before investigating an
unexpected condition. Do not start a second host against the same robot.

## 1. Record the environment

```sh
cat VERSION
bin/doctor.sh
```

Keep the doctor's output and exit status. It checks board compatibility
and the available binaries; it does not validate cameras, servo wiring
or calibration. With a capsule supplied, it also interprets native
preflight results. The runners perform that preflight with their generated
capsule. The public build's expected observer refusal is explained in
[Limitations](../LIMITATIONS.md#the-preflight-cannot-reach-pass-in-the-public-build).
Any other refusal needs investigation.

For a downloaded archive, record `version` and `source_revision` from
the archive's top-level `MANIFEST.txt`. For a Git checkout, also record:

```sh
git rev-parse HEAD
git status --short
```

For segment 2, include the LeRobot revision on both machines, Python
version, whether the documented clamp fix was applied, and any other
local changes. Matching Cake identities do not establish that these
external files match another run.

## 2. Find the first failed step

The startup line names the run ID; a completed run also prints its
directory. By default it is `state/runs/<id>/`; `KC_STATE_DIR` changes the
state root. If startup refuses before a run ID appears, use the terminal
output: no transcript has been created yet. Otherwise, start with
`transcript.txt` and the first `FAILED` line, then read the output before
it. Later cleanup output is useful but may describe a consequence of the
initial failure.

| File within the run directory | Use it for |
| --- | --- |
| `transcript.txt` | Step order, first failure, process IDs and reported checks |
| `manifest.txt`, `demo-plan.err` | Generated Plan and store paths, capsule identity, bundle creation errors |
| `preflight.out`, `preflight.err` | Which admission or platform check passed or refused |
| `poll-before.txt`, `poll-after.txt` | Segment 1 status and events before and after resident relaunch |
| `first.out`, `first.err`, `second.out`, `second.err` | Segment 1 resident output for the two sessions |
| `tampered.out`, `tampered.err` | Segment 1's deliberate package-tampering refusal |
| `poll-1.txt` | Segment 2's initial admin snapshot |
| `safe-stop.log` | Whether the demo's logging hook ran |

Only files for stages the runner reached will exist. The run's lowercase
`manifest.txt` is generated by `demo-plan`; it is different from the
release archive's top-level `MANIFEST.txt`.

In segment 2, also inspect the resident's systemd journal and the host's
captured `supervisor.log` in the module data directory under the run's
`store_root`. Use the generated manifest to identify that store. The
[journal procedure](stopping-and-cleanup.md#what-was-measured)
covers Raspberry Pi OS setups where `journalctl --user` is empty. Host
stderr is often the evidence that explains a repeated child exit.

## 3. Read the live lifecycle evidence

While segment 2 is running, from another Pi terminal:

```sh
bin/telemetry.sh --rounds 1 --flight-rows 10
systemctl --user status --no-pager kiwi-cake-demo.service
```

The telemetry command uses the live segment's default socket. For segment
1, pass `--socket` with the per-run socket path printed in its transcript.
Keep the default positive query timeout; setting `KC_PROBE_TIMEOUT=0`
disables it. A failed query is evidence of unavailable telemetry, not
proof that the robot is stopped.

| Observation | Interpretation | Follow-up |
| --- | --- | --- |
| `EVT_SUPERVISOR_CHILD_EXITED`, then `EVT_SUPERVISOR_CHILD_STARTED` at a later sequence | A child exit and another launch were observed | Read the exit status and host stderr; check whether the runner intentionally sent a signal |
| Restart ordinal increases in the same session | The supervisor restarted its child | Check the new host's output and readiness; launch alone does not prove usable observations |
| `EVT_SUPERVISOR_RESTART_BOUND_REACHED` | The configured restart policy stopped retrying | Inspect the earliest host error before attempting another run |
| New session, other four identities unchanged | A fresh resident activated the same declared configuration | Compare external host, dependency and calibration versions separately |
| `poll queries answered 3 of 3` | The poll counted its three required admin queries as answered | Inspect the actual slot and event rows; the summary is not a robot health check |
| A new `safe-stop.log` line | The supplied hook appended a line | It proves no motor action; observe physical state separately |

Use [Event codes](event-codes.md) for argument meanings. Preserve sequence
numbers and the events around a failure. The flight ring is bounded to
256 records, and admin queries themselves add events: it is not a durable
history of the whole run. Capture relevant output before it is displaced.

A successful segment 1 run ends with `KIWI-CAKE SEGMENT 1: PASS`. Segment
2 can end successfully with teleoperation explicitly `SKIPPED`; that
does not establish that the laptop client connected or the arm followed
the leader. Report the teleoperation outcome separately.

## 4. Narrow down common symptoms

These are starting points for investigation, not automatic diagnoses.

| Symptom | Next check |
| --- | --- |
| Host repeatedly exits during startup | Look for a calibration prompt or `EOFError`; confirm the noninteractive wrapper and loaded calibration file, then inspect camera and serial errors |
| `Message fetching failed: 'arm_shoulder_pan.pos'` | Check the pinned LeRobot revision and documented clamp fix |
| `Message fetching failed: 'x.vel'` | Check that the client sends the three base velocity fields; the supplied client sends zero values |
| `Cycle time reached.` followed by restart | Check `--host.connection_time_s`; an intentional host lifetime expiry is not itself a crash |
| Laptop cannot receive observations | Check host readiness, the configured Pi address, camera errors and reachability of TCP 5555/5556 on your trusted LAN |
| A configured port is already listening, or listener ownership is unexpected | Identify the existing process before continuing; the runner can warn about an unexpected owner without refusing it |
| Empty, malformed or unavailable telemetry rows | Keep the raw output and stderr; do not infer a healthy host from the table's summary |

If you need to test the host by hand, first stop the resident and verify
that its child and listeners are gone. Then use the stand precautions and
standalone-host step in the [runbook](reproduce-end-to-end.md). Starting
another host while the first still owns the hardware can create a second
problem and obscure the original one.

## 5. Share a useful reproduction report

Open an [issue](https://github.com/shinro-dev/kiwi-cake-demo/issues) using
the checklist in [Contributing](../CONTRIBUTING.md). Include:

- the question you were investigating, expected behavior and first failed
  step;
- release/source revisions, board facts and relevant local changes;
- the commands used and selected transcript, host-error and event excerpts;
- whether a robot was connected, whether teleoperation ran or was skipped,
  and what you physically observed;
- what the evidence helped you determine, and what you still had to
  investigate outside the demo.

Select and review text files manually. There is no support-bundle command.
Do not upload the whole `state/` or run directory: it can contain private
keys, including `state/keys/demo.keypair` and a run's `control.keypair`,
as well as local configuration. Remove private paths, hostnames, network
addresses, device identifiers and personal data from excerpts. Use
consistent placeholders so before/after comparisons remain readable.
For a suspected vulnerability, use [private reporting](../SECURITY.md)
instead of a public issue.
